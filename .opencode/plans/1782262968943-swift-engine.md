# Plan: Remove Hardcoded Rebalance Decision Rules

## Goal

Bring the new `icu rebalance` implementation back into compliance with `AGENTS.md` by removing hidden hardcoded physiological, training-load, workout-intensity, scheduling, and planning decisions.

The replacement rule is simple: if rebalance cannot derive a decision from athlete data, sport settings, recent history, event context, or explicit user input, it must not silently invent a default. It should either mark the proposal infeasible or require an explicit constraint.

## Critical Files

- `rebalance.go`: core DTOs, dynamic targets, baseline, allocation, scoring, operation generation.
- `rebalance_test.go`: core compliance and replay-style tests.
- `cmd/icu/cmd_rebalance.go`: CLI input collection and explicit flags.
- `cmd/icu/cmd_rebalance_test.go`: CLI flag and fetch behavior tests.
- `docs/rebalance.md`: workflow, dynamic decision behavior, infeasible cases.
- `docs/cli-reference.md`: command contract and flags.
- `docs/library.md`: exported API behavior.

## Problems To Fix

### 1. Hidden Target Tolerance

Current issue: feasibility tolerance uses hidden defaults such as absolute/percentage load tolerances.

Fix:
- Add `RebalanceTargets.TargetTolerance` and `TargetToleranceSource` or equivalent labelled fields.
- Derive tolerance from recent historical weekly load variability using MAD/robust statistics when enough history exists.
- If history is sparse and no explicit tolerance was provided, use a blocking validation gate instead of a fallback numeric default.
- Add CLI `--target-tolerance N` so the user can provide an explicit one-run constraint.

Tests:
- Stable history derives small tolerance.
- Volatile history derives larger tolerance.
- Explicit tolerance overrides derived tolerance.
- Sparse history without explicit tolerance blocks proposal generation or marks it infeasible.

### 2. Fallback IF Values

Current issue: fallback Z1/Z2 IF values are hardcoded.

Fix:
- Remove fallback IF generation.
- Prefer sport power zones.
- If no zones, derive endurance intensity from recent cycling activity intensity distribution after MAD outlier filtering.
- Derive lower/easier target from actual low-intensity historical samples, not `z2 * constant`.
- If neither sport settings nor enough history nor explicit `--z1-if/--z2-if` exist, do not generate workout operations; emit blocking validation explaining missing intensity basis.

Tests:
- Sport settings drive IF.
- Historical low/easy samples drive IF.
- Outlier intensity is ignored.
- No data and no explicit IF produces blocking validation/no operations.
- Explicit IF allows generation.

### 3. Strategy And Replace Intensity Defaults

Current issue: strategy and replace-intensity defaults are hardcoded and partly unused.

Fix:
- Support exactly one strategy for now: `target-preserving-z2`.
- Validate `Request.Strategy`; unsupported strategies become blocking validation errors.
- Remove hidden `ReplaceIntensity` defaults unless they are implemented.
- If replacement filtering remains, derive replaceable classification from sport zones/history and honor only explicit user input.

Tests:
- Empty strategy normalizes to the single supported strategy with a labelled source.
- Explicit supported strategy works.
- Unsupported strategy blocks validation.
- Removed/unused replace-intensity behavior is not emitted as a false promise.

### 4. Hardcoded Ride/POWER Event Type

Current issue: generated events always use `Type: "Ride"` and `Target: "POWER"`.

Fix:
- Add explicit `SportType` and `TargetType` to `RebalanceInput` or `RebalanceConstraints`.
- CLI populates `SportType` from existing `--type`.
- Updates preserve the existing event type and target where possible.
- Creates use explicit/inferred `SportType`; no hidden Ride fallback.
- POWER workouts require FTP/power-zone basis or explicit IF/watts. If unavailable, block rather than creating invalid power sessions.

Tests:
- `--type Ride` creates Ride.
- Non-Ride without supported power basis blocks or creates only when explicit supported target data exists.
- Update operation preserves existing event type.
- Missing sport type produces a clear validation error.

### 5. Hardcoded Calendar Time

Current issue: created/updated events use `T00:00:00`.

Fix:
- Updates preserve the existing event local time.
- Creates derive preferred start time from recent activity/event history for the same weekday when enough samples exist.
- Add explicit CLI `--start-time HH:MM` as a user-provided constraint.
- If there is no history and no explicit time, block create operations or create no-op proposal rather than scheduling midnight.

Tests:
- Update preserves original time.
- Create uses same-weekday historical median start time.
- Explicit `--start-time` overrides history.
- Sparse history without explicit time blocks create operations.

### 6. Hardcoded Duration Minimum And Rounding

Current issue: session duration minimum and rounding step are fixed.

Fix:
- Derive normal session duration granularity from recent planned/completed workout durations when enough data exists.
- Add explicit `--min-session-minutes` and `--duration-step-minutes` constraints if needed.
- If no basis exists, avoid generating duration-dependent workouts unless explicit constraints are provided.

Tests:
- History with 10-minute granularity derives 10-minute step.
- Explicit duration constraints override history.
- Sparse history without explicit duration basis blocks generation.

### 7. Uniform Load Distribution

Current issue: load is split evenly across slots in date order.

Fix:
- Derive per-day allocation weights from athlete historical day-of-week load/session distribution, after robust outlier filtering.
- Preserve existing mutable event load shape when updating instead of flattening everything equally.
- If history is sparse, require explicit allowed day weights or keep existing mutable events unchanged and mark unmet target as infeasible.
- Do not cancel events solely because an earlier uniform allocation consumed the target; cancellation must be tied to explicit `AllowCancel` plus a derived/validated reason.

Tests:
- Weekend-heavy history allocates proportionally to weekend.
- Weekday-heavy history allocates proportionally to weekdays.
- Existing mutable event shape is preserved when possible.
- Sparse history does not invent equal distribution.
- Cancel disabled preserves mutable events.

### 8. Hardcoded Classification Thresholds

Current issue: event classification uses fixed IF thresholds and a two-hour long-ride fallback.

Fix:
- Classify intensities from sport power zones where available.
- Otherwise classify from athlete historical intensity clusters/percentiles with MAD filtering.
- Derive long-session threshold from historical moving-time distribution.
- If unavailable, label classification `unknown` and lower confidence instead of applying fixed thresholds.

Tests:
- Sport-zone classification identifies recovery/aerobic/tempo.
- Historical classification adapts to athlete history.
- Long-ride threshold responds to history and outliers.
- Sparse data yields `unknown`, not hardcoded categories.

### 9. Hardcoded Score Penalties

Current issue: option score uses fixed penalties.

Fix:
- Remove numeric score from v1, or replace it with transparent validation/evaluation fields only.
- Preferred minimal fix: remove `Score` calculation/output unless a dynamic scoring basis is implemented.

Tests:
- Proposal no longer emits misleading fixed score, or score source is explicit and dynamic.
- Validation/evaluation still explains target delta and warnings.

### 10. Fixed Wellness Lookback

Current issue: CLI always fetches 42 days.

Fix:
- Add explicit `--wellness-lookback-days N`, or derive from existing wellness analysis requirements if such a constant already exists and is documented as an analysis window.
- If kept as protocol/analysis input, document it as an explicit CLI default and not a decision threshold.

Tests:
- Default documented window is used.
- Explicit lookback changes wellness fetch start date.

### 11. Today/Past Locking

Current issue: date-based locking can over-lock planned events just because date <= now.

Fix:
- Completed activities lock matching dates.
- Existing event status/category/context locks races and target events.
- Past planned events are locked by default only as a safety rule, with explicit `--allow-past` or existing `AllowToday` for today if needed.
- Keep the safety rule documented because it affects mutation behavior.

Tests:
- Completed activity locks matching date.
- Planned today is mutable only with explicit allow-today.
- Past event lock is documented and can be explicitly overridden if supported.
- Race/target events remain immutable.

## Implementation Order

1. Write failing tests first for the highest-risk violations: no fallback IF, no midnight creates, no uniform allocation with sparse history, no fixed score.
2. Extend DTOs minimally with labelled source fields required to audit decisions.
3. Remove hidden defaults before adding new behavior.
4. Add explicit CLI flags only when the user can supply a real one-run constraint.
5. Update docs in the same change for every public behavior change.
6. Run full quality gates.

## Acceptance Criteria

- No hidden hardcoded physiological, intensity, training-load, scheduling, or planning thresholds remain in rebalance.
- Every generated operation has auditable sources for sport, target type, intensity, duration, start time, allocation, and tolerance.
- Missing/sparse data produces lower confidence or blocking validation, not invented defaults.
- Public docs describe explicit user constraints and dynamic derivation sources.
- Rebalance tests include representative history, sparse history, outliers, and already-completed sessions.
