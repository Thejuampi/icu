# Plan: Micro-Analysis CLI Infrastructure

## 1. Gap Analysis — What the CLI Cannot Do Today

| # | Gap | Root Cause |
|---|---|---|
| 1 | **Warmup HR efficiency** (HR slope first 600s) | No section detection; no time-series processing primitives |
| 2 | **Cooldown HR recovery** (HR decay last 600s) | Same as #1 |
| 3 | **Power:HR zone alignment per session** (macro-computable already but not exposed per-session) | `CyclingSession` lacks `ZoneTimes` and `HRZoneTimes`; analysis.go only aggregates them |
| 4 | **Interval repeatability** (power/HR consistency per rep) | `IntervalsDTO` exists in types.go but zero analysis functions consume it |
| 5 | **Per-segment EF** (warmup vs main vs cooldown EF) | No section detection; no per-segment metric extraction |
| 6 | **HRR (1-min, 2-min post-peak)** | Requires sorted time-series with peak detection |
| 7 | **Session-level zone alignment** in analysis output | `CyclingSession` struct is missing `ZoneTimes`/`HRZoneTimes` fields |
| 8 | **No `analysis micro` command** | No CLI surface exists for single-activity analysis |

---

## 2. API Endpoints & Fields That Fill the Gaps

All three already have CLI read commands and DTOs:

| Data | Endpoint | CLI Command | DTO |
|------|----------|-------------|-----|
| Raw time-series | `GET /api/v1/activity/{id}/streams` | `activity <id> streams` | `[]ActivityStream` |
| Detected intervals | `GET /api/v1/activity/{id}/intervals` | `activity <id> intervals` | `IntervalsDTO` |
| Full activity detail | `GET /api/v1/activity/{id}` | `activity <id> show` | `Activity` (170+ fields) |

`activity <id> show` already returns `Activity` with `ZoneTimes` and `HRZoneTimes`. The gap is in the analysis layer, not the API layer.

## 3. Design: Bottom-Up Layered Architecture

### Layer 1 — Data Access (imperative shell, no changes needed)
```
client.Get("activity", []string{id}, nil, &activity)      // already exists
client.Get("activity", []string{id, "streams"}, q, &streams)  // already exists
client.Get("activity", []string{id, "intervals"}, nil, &dto)   // already exists
```
**No new data-access code.**

### Layer 2 — Normalization / Internal Models (functional core)

**New file: `norm.go`** — Normalize raw API responses into typed, aligned data.

```go
// StreamData holds aligned time-series values indexed by stream type.
// Each stream type (watts, heartrate, cadence) maps to a []float64.
// All slices share the same length and index = time step.
type StreamData map[string][]float64

// NormalizeStreams converts raw []ActivityStream into aligned StreamData.
// Handles: type dispatch, array coercion (Data can be []int, []float64, []any),
// empty stream checks, length mismatch detection.
func NormalizeStreams(raw []ActivityStream) (StreamData, error)
```

**Tests needed:** `norm_test.go`
- Empty streams list → empty StreamData
- Single stream with []float64 data → correct key
- Multiple streams (watts, heartrate) → both keys present, equal length
- Mixed []int / []float64 Data → both coerced to []float64
- Length mismatch → error
- Stream with all-nulls → included but marked

### Layer 3 — Segmentation (functional core)

**New file: `segments.go`** — Identify analysable sections from time-series data.

```go
// ActivitySection labels a contiguous range within an activity.
type ActivitySection struct {
    Name       string   // "warmup", "main", "cooldown", "interval_1", "recovery_1", ...
    StartIndex int      // inclusive
    EndIndex   int      // exclusive
    Metadata   map[string]any  // optional: zone, target, labels
}

// Section detection strategies:

// DetectSectionsByPowerZones splits activity by power zone transitions
// using configured FTP. Returns labeled segments like "z1_warmup", "z3_tempo", "z1_cooldown".
func DetectSectionsByPowerZones(watts []float64, ftp int) []ActivitySection

// DetectSectionsByRPE proxies "warmup" as first N minutes where power is rising
// and "cooldown" as last N minutes where power is falling below baseline.
func DetectSectionsBySlope(watts []float64, seconds int) (warmup ActivitySection, cooldown ActivitySection, main ActivitySection)

// DetectIntervalsFromDTO converts IntervalsDTO intervals into ActivitySection slices.
// Groups intervals by type (work vs recovery) and labels them.
func DetectIntervalsFromDTO(dto IntervalsDTO) []ActivitySection

// DetectSectionsByHRStabilization detects warmup as the period until HR
// stabilizes (variance drops below threshold) and cooldown as the final
// declining phase.
func DetectSectionsByHRStabilization(hr, watts []float64) (warmup ActivitySection, cooldown ActivitySection)
```

**Design rule**: Each detection function returns labelled sections. The caller decides which sections to extract and what to do with them. Detection functions do NOT emit analysis conclusions.

**Tests needed:** `segments_test.go`
- Power zone detection: rising + sustained Z3 + falling → 3+ sections correctly labeled
- Slope-based: flat power before, rising first 20%, flat middle, dropping last 10% → warmup/main/cooldown
- HR stabilization: drifting HR at start, stable HR middle, declining HR end → correct boundaries
- Empty watts → zero sections
- Constant power (no zones crossed) → single section
- Intervals from DTO: 4 work + 4 recovery → 8 sections with correct labels
- Overlap check: section boundaries must be contiguous and non-overlapping

### Layer 4 — Generic Metrics (functional core)

**New file: `metrics.go`** — Pure statistical/physiological functions over numeric slices.

```go
// All functions accept []float64 slices and return computed values.
// Zero knowledge of CLI, HTTP, or domain context.

func AveragePower(watts []float64, start, end int) float64
func AverageHeartRate(hr []float64, start, end int) float64
func NormalizedPower(watts []float64, start, end int) float64
func MaxValue(data []float64) float64

// HeartRateDrift computes HR drift over a section as the slope of
// a linear regression HR vs time (10-sec rolling avg to smooth noise).
func HeartRateDrift(hr []float64, seconds int) float64

// PowerHRRatio computes average watts-per-bpm over a section.
func PowerHRRatio(watts, hr []float64, start, end int) float64

// Decoupling computes (HR:power ratio second half) / (HR:power ratio first half) - 1.
func Decoupling(watts, hr []float64) float64

// TimeInZone counts seconds where power falls within [minPct, maxPct] of FTP.
func TimeInZone(watts []float64, ftp int, minPct, maxPct float64) int

// HeartRateRecovery computes bpm drop over a window after peak HR.
// Returns bpm drop per minute over the specified window.
func HeartRateRecovery(hr []float64, peakIndex, windowSize int) float64

// Slope computes linear regression slope over a data slice.
func Slope(data []float64) float64

// Variance computes the variance of a data slice.
func Variance(data []float64) float64

// HeartRateToLTHR converts bpm to percentage of LTHR.
func HeartRateToLTHR(hr float64, lthr int) float64
```

**Rule**: Every function must be independently testable. Inputs: slices + indices or boundaries. Outputs: float64/int. No structs, no state, no IO.

**Tests needed:** `metrics_test.go`
- AveragePower: known slice → correct mean
- NormalizedPower: known 30s rolling average + 4th power formula → correct NP
- HeartRateDrift: linearly increasing HR → positive slope; decreasing → negative; flat → ~0
- PowerHRRatio: equal values → 1.0; watts > hr → > 1.0
- TimeInZone: watts around FTP → correct seconds per zone
- HeartRateRecovery: dropping HR → positive recovery rate
- Empty slice → 0 (no panic)
- Single element → that value
- Boundary cases: start == end, start > end

### Layer 5 — Domain Analysis (functional core)

**New file: `micro_analysis.go`** — Combines segments + metrics to answer coaching questions.

```go
// ActivityMicroAnalysis is the per-activity analysis output type.
type ActivityMicroAnalysis struct {
    ActivityID    string                        `json:"activityId"`
    ActivityName  string                        `json:"activityName"`
    Warmup       *WarmupAnalysis               `json:"warmup,omitempty"`
    Cooldown     *CooldownAnalysis             `json:"cooldown,omitempty"`
    Intervals    *IntervalAnalysis             `json:"intervals,omitempty"`
    ZoneAlignment ZoneAlignmentAnalysis         `json:"zoneAlignment,omitempty"`
    SessionSummary *CyclingSession             `json:"sessionSummary"`
}

type WarmupAnalysis struct {
    DurationSeconds   int     `json:"durationSeconds"`
    AvgPower         float64  `json:"avgPower"`
    AvgHR            float64  `json:"avgHr"`
    HRStabilization  int      `json:"hrStabilizationSeconds"` // time to HR plateau
    HREfficiency     float64  `json:"hrEfficiency"`            // power:HR ratio
    HRSlope          float64  `json:"hrSlope"`                 // bpm per minute rise
}

type CooldownAnalysis struct {
    DurationSeconds   int     `json:"durationSeconds"`
    AvgPower         float64  `json:"avgPower"`
    AvgHR            float64  `json:"avgHr"`
    HRRecovery1Min   float64  `json:"hrRecovery1Min"`  // bpm drop in 1st minute
    HRRecovery2Min   float64  `json:"hrRecovery2Min"`  // bpm drop in 2nd minute
    HRDecayRate      float64  `json:"hrDecayRate"`     // bpm/min
}

type IntervalAnalysis struct {
    RepCount         int                    `json:"repCount"`
    WorkDuration     float64                `json:"workDurationSecs"`
    RecoveryDuration float64                `json:"recoveryDurationSecs"`
    Reps             []IntervalRepAnalysis  `json:"reps"`
    Repeatability    RepeatabilityAnalysis  `json:"repeatability"`
}

type IntervalRepAnalysis struct {
    Index             int     `json:"index"`
    Type              string  `json:"type"` // "work" or "recovery"
    AvgPower          float64 `json:"avgPower"`
    AvgHR             float64 `json:"avgHr"`
    MaxHR             float64 `json:"maxHr"`
    EF                float64 `json:"ef"`
    DurationSeconds   int     `json:"durationSeconds"`
}

type RepeatabilityAnalysis struct {
    WorkPowerMean     float64 `json:"workPowerMean"`
    WorkPowerStdDev   float64 `json:"workPowerStdDev"`
    WorkPowerCV       float64 `json:"workPowerCV"`
    WorkHRMean        float64 `json:"workHrMean"`
    WorkHRStdDev      float64 `json:"workHrStdDev"`
    PowerDrift        float64 `json:"powerDrift"`   // first rep power - last rep power
    HRDrift           float64 `json:"hrDrift"`      // last rep HR - first rep HR
}

type ZoneAlignmentAnalysis struct {
    PowerZ1Z2Pct      float64 `json:"powerZ1Z2Pct"`
    HRZ1Z2Pct         float64 `json:"hrZ1Z2Pct"`
    PowerZ3PlusPct    float64 `json:"powerZ3PlusPct"`
    HRZ3PlusPct       float64 `json:"hrZ3PlusPct"`
    AlignmentGap      float64 `json:"alignmentGap"`  // HR_Z3+% - Power_Z3+%
    HROneZoneAbove    float64 `json:"hrOneZoneAbove"` // % time HR in Z4 when Power in Z2-Z3
    Diagnosis         string  `json:"diagnosis"`     // "normal", "hot", "cold"
}

// Top-level analysis functions:
func AnalyzeWarmup(watts, hr []float64, warmupSection ActivitySection, lthr int) WarmupAnalysis
func AnalyzeCooldown(watts, hr []float64, cooldownSection ActivitySection, lthr int) CooldownAnalysis
func AnalyzeIntervals(sections []ActivitySection, watts, hr []float64, ftp int) IntervalAnalysis
func AnalyzeZoneAlignment(zoneTimes []ZoneTime, hrZoneTimes []int) ZoneAlignmentAnalysis

// Orchestrator — combines everything for a single activity:
func AnalyzeActivityMicro(activity Activity, streams StreamData, intervals IntervalsDTO, ftp, lthr int) ActivityMicroAnalysis
```

**Function contract**: Each `AnalyzeX` function accepts pre-detected sections and raw data. It does NOT call detection functions internally. This keeps analysis functions independently testable.

**Tests needed:** `micro_analysis_test.go`
- Warmup with rising HR → HRStabilization > 0, HRSlope > 0
- Warmup where HR is already stable → HRStabilization ≈ 0
- Cooldown with falling HR → positive recovery rates
- Intervals: 4 reps with equal power → CV < 3%, PowerDrift ≈ 0
- Intervals: fading power (last rep 10% lower) → negative PowerDrift, higher CV
- Zone alignment: matched zones → gap ≈ 0, diagnosis "normal"
- Zone alignment: HR 1 zone above power → positive gap, diagnosis "hot"
- No intervals (empty DTO) → intervals analysis nil, no panic
- No streams → warmup/cooldown nil (graceful degradation)

### Layer 6 — CLI Command (imperative shell)

**New file section in `cmd_analysis.go`** — Register `analysis micro`:

```bash
icu analysis micro <activityId> [--ftp FTP] [--lthr LTHR]
```

The command:
1. Fetches `activity <id> show`, `activity <id> streams`, `activity <id> intervals`
2. Normalizes streams via `icu.NormalizeStreams()`
3. Detects sections via `icu.DetectSectionsByHRStabilization()` (+ power-based fallback)
4. Calls `icu.AnalyzeActivityMicro(activity, streams, intervals, ftp, lthr)`
5. Outputs JSON

**Also:** Extend `CyclingSession` to include `ZoneTimes` and `HRZoneTimes` so the existing `analysis cycling` output carries per-session zone data for the zone-alignment micro metric.

## 5. What NOT to Abstract Yet (KISS / YAGNI)

| Idea | Why skip |
|---|---|
| Generic "time-series DB" or "stream engine" | Over-engineering; we have `[]float64` slices, not TB-scale data |
| Custom interval detection algorithm | Intervals.icu already auto-detects intervals; consume, don't reinvent |
| Multi-activity batch micro analysis command | Compose from single-activity analysis; no dedicated multi-activity layer needed yet |
| HTML/PDF report rendering | JSON is the output contract; rendering is UI-layer concern |
| Cadence analysis in warmup/cooldown | Cadence data is available but not requested by current use cases; add when needed |
| GAP / elevation impact analysis | Same — available in streams but not requested |
| Per-second streaming analytics | Intervals.icu streams are already ~1Hz; no sub-second needs |

## 6. Implementation Order

| Phase | Files | Items | Rationale |
|---|---|---|---|
| **1** | `metrics.go` + `metrics_test.go` | All metric functions (AveragePower through HeartRateToLTHR) | Foundation — everything else depends on these. Pure, testable in isolation. |
| **2** | `norm.go` + `norm_test.go` | `NormalizeStreams()`, `StreamData` type | Unblocks stream-based metrics. |
| **3** | `segments.go` + `segments_test.go` | Section detection functions | Unblocks section-specific analysis. |
| **4** | `micro_analysis.go` + `micro_analysis_test.go` | All analysis types + `AnalyzeActivityMicro()` | Composes layers 1-3 into domain answers. |
| **5** | `analysis.go` (patch) | Add `ZoneTimes`/`HRZoneTimes` to `CyclingSession` + update `cyclingSessionFromActivity` | Closes gap #7 without breaking JSON contract. |
| **6** | `cmd_analysis.go` (patch) | Register `analysis micro` command | Final CLI surface. |

Each phase is independently compilable, testable, and produces zero lint/vet issues before moving to the next.
