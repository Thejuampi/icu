# Plan: Planned Workout Execution Analysis

## Recommendation

Add a new read-only command under `analysis` that evaluates one completed activity against its planned workout context in one pass.

Recommended CLI:

```bash
icu analysis workout <activity-id> [--event-id ID] [--calendar-id ID] [--sport-type TYPE] [--match-window-hours N]
```

Why this shape:
- Keeps the feature explicitly analysis-oriented instead of overloading `activity show`.
- Lets the CLI fetch all required sources in one call: activity, streams, intervals, candidate events, sport settings.
- Produces a stable JSON contract for downstream coaching/report skills.

## Core Problem To Solve

Today the repo has enough execution-side primitives to analyze how a workout was ridden, but not enough plan-side structure to say how that execution compared to the intended workout.

Current gaps:
- `activity show --intervals` sends the query but does not surface embedded intervals in `Activity`.
- `Event.WorkoutDoc` and `Workout.WorkoutDoc` are untyped `any` values.
- No analyzer currently joins planned workout structure to streams/intervals.
- Microcycle and plan analyzers stop at session/event level.

## Implementation Approach

### 1. Add typed planned-workout structures

Create typed DTOs for workout structure without breaking existing `any` fields.

Files:
- `types.go`
- new `workout_doc.go`
- `event_json.go`

Plan:
- Keep `Event.WorkoutDoc any` and `Workout.WorkoutDoc any` for compatibility.
- Add typed decode helpers, not replacement fields.
- Introduce types for:
  - `WorkoutDoc`
  - `WorkoutStep`
  - `WorkoutTarget`
  - flattened/expanded `PlannedWorkoutStep`
- Add helpers to:
  - decode `workout_doc`
  - optionally decode `workout_file_base64` when present
  - expand repeats into explicit step instances
  - resolve step targets into comparable values using FTP/LTHR

### 2. Add workout-event matching

Create a pure matcher that links one completed activity to the best planned event.

New file:
- `workout_execution_analysis.go`

Matching order:
- explicit `--event-id`
- otherwise same-day / nearby `WORKOUT` events within a default window
- score candidates by:
  - category
  - sport/type similarity
  - start-time proximity
  - duration similarity
  - load similarity
  - name similarity
  - presence of decodable structured workout data

Return:
- best match
- confidence
- reasons
- alternate candidates when ambiguous

### 3. Build a full planned-vs-executed analyzer

Create a new exported analysis API that joins plan and execution.

New library API:
- `AnalyzeWorkoutExecution(inputs WorkoutExecutionInputs, options WorkoutExecutionOptions) WorkoutExecutionAnalysis`

Inputs:
- `Activity`
- normalized `StreamData`
- `IntervalsDTO`
- candidate `[]Event`
- `SportSettings`

Output contract:
- `scope`
- `activity`
- `match`
- `plan`
- `execution`
- `comparison`
- `warnings`

Comparison levels:
- session-level: duration, load, intensity, distance, completion status
- block/rep-level: planned reps vs executed reps, work/recovery duration drift, interval repeatability, HR drift
- step-level where possible: target zone/power/HR/cadence adherence, completion status, deviation, notes

### 4. Reuse existing execution-side analyzers

Leverage existing code instead of rebuilding stream logic.

Critical reuse:
- `norm.go` for `NormalizeStreams`
- `micro_analysis.go` for warmup, cooldown, intervals, repeatability, zone alignment
- `segments.go` for interval section extraction

Alignment rule:
- use planned workout order as the primary frame
- use interval boundaries when available
- otherwise fall back to planned durations plus stream-derived local changes
- emit warnings when alignment confidence is low

### 5. Wire the new CLI command

Add `analysis workout` in the existing analysis registry.

Files:
- `cmd/icu/cmd_analysis.go`
- `cmd/icu/cmd_analysis_test.go`
- `cmd/icu/command_functional_test.go`

Fetch flow:
- get activity by ID with required fields
- get activity intervals
- get activity streams (`watts,heartrate,cadence` by default)
- fetch candidate events around activity local date, optionally filtered by `calendar-id`
- fetch sport settings
- call the new analyzer
- write JSON

### 6. Keep degradation explicit

The command must stay useful when data is partial.

Fallback hierarchy:
- full step/block comparison when plan + streams + intervals exist
- block/rep comparison when plan + intervals exist
- time-sliced comparison when plan + streams exist
- session-only comparison when only event summary exists
- match-only output when no structured plan exists

Warnings instead of fabricated precision:
- no plan found
- ambiguous plan match
- workout doc decode failure
- missing streams
- missing intervals
- missing power/HR/cadence
- missing FTP/LTHR
- low-confidence alignment
- unsupported freeride / until-lap behavior
