# Precise Planned Load Calculation

## Goal

Make the CLI calculate planned cycling workout duration, IF, NP-like power, and TSS locally before posting/updating Intervals.icu events, so deload and block planning can be validated without relying on a server round trip.

## Recommended Approach

Build this as a functional-core feature first, then wire it into CLI flows. Keep the parser explicit and test-backed instead of trying to silently clone every undocumented Intervals.icu parser behavior in one pass.

## Scope

- Support cycling power-based planned load first.
- Use FTP from explicit input or sport settings.
- Parse the workout description grammar used by this CLI and coaching workflow.
- Validate local results against Intervals.icu-generated `workoutDoc`/`icuTrainingLoad` before using the values automatically.
- Do not add HR, pace, swimming, running, calories, or device-file parsing until cycling power load is stable.

## Design

1. Add a pure workout-description parser.
   - New file: `workout_description.go`.
   - Parse line-oriented workout text into existing `WorkoutDoc` / `WorkoutStep` types.
   - Supported grammar for first implementation:
     - Step lines: `- 10m 55-75%`, `- 5m 90%`, `- 30s 120%`.
     - Repeat blocks: `3x` with indented `-` child steps.
     - Keywords in step text: warmup, cooldown, recovery, work.
     - Power targets as `%ftp` only.
     - Ramps when a range is provided, e.g. `55-75%`.
   - Reject ambiguous text with a structured warning/error instead of guessing.

2. Add pure planned-load calculation.
   - New file: `planned_load.go`.
   - Input: `WorkoutDoc`, FTP.
   - Output: `PlannedLoadEstimate` with duration seconds, average power, normalized power, IF, TSS, source, warnings.
   - Reuse `ExpandWorkoutSteps` and `NormalizedPower` from `metrics.go`.
   - Generate a one-second planned watts series from expanded steps:
     - Steady target: constant watts.
     - Range/ramp target: linearly interpolate start to end across the step.
     - Repeat blocks: already handled by `ExpandWorkoutSteps`.
   - Formula:
     - `IF = NP / FTP`.
     - `TSS = durationHours * IF * IF * 100`.
   - Round display values only at the boundary; keep internal math as `float64`.

3. Add validation against Intervals.icu output.
   - Compare local estimate with server-returned event fields when available:
     - Duration vs `Event.MovingTime`.
     - TSS vs `Event.TrainingLoad`.
     - IF vs `Event.Intensity`.
   - Add tolerance constants in one place:
     - Duration exact or within 1 second.
     - TSS within 1-2 points initially.
     - IF within 0.01.
   - If mismatch exceeds tolerance, report warnings and keep server value as authoritative for persisted analysis.

4. Add dry-run CLI and explicit event auto-fill together.
   - Dry-run command: `icu workouts calculate --ftp N --desc DESC`.
   - Output JSON with parsed doc summary, duration, NP, IF, TSS, warnings.
   - Event integration: `events create/update --calculate-load --ftp N --desc DESC`.
   - Auto-fill is explicit only. Do not silently calculate load just because `--desc` exists.
   - When `--calculate-load` is set, parse `--desc`, compute `moving_time` and `icu_training_load`, and include them in the request.

5. Wire planned-load fallback into analysis.
   - In `planning_analysis.go`, when an event has missing/stale `TrainingLoad` but has `WorkoutDoc`, calculate local load and mark the source.
   - Preserve existing server fields as authoritative when present and valid.
   - Extend `TrainingPlanSession` only if needed to expose load source/warnings.

6. Keep server comparison as the safety rail.
   - After create/update returns, compare local calculated values with returned server fields when present.
   - Print/return warnings on mismatches outside tolerance.
   - Server values remain authoritative for persisted analysis until calibration proves local parity.

## Critical Files

- `workout_doc.go`: existing `WorkoutDoc`, `WorkoutStep`, `WorkoutTarget`, and `ExpandWorkoutSteps`.
- `metrics.go`: existing `NormalizedPower` function.
- `planning_analysis.go`: current plan sessions use `Event.TrainingLoad`; add local fallback here.
- `workout_execution_analysis.go`: currently has local `%ftp` conversion; move/reuse equivalent logic in the new planned-load core.
- `cmd/icu/cmd_events.go`: `events create/update --calculate-load` integration.
- `cmd/icu/cmd_workouts.go`: likely home for `workouts calculate`.
- `docs/cli-reference.md`: document new command/flags/output.
- `docs/analysis.md`: document analysis fallback/source behavior if plan analysis changes.

## Tests First

Add failing tests before implementation:

- `workout_description_test.go`
  - Parses one steady step.
  - Parses ramp step.
  - Parses repeat block.
  - Rejects ambiguous unsupported text.
  - Preserves warmup/cooldown/recovery text classification.

- `planned_load_test.go`
  - Steady 60m at 70% FTP gives IF 0.70 and TSS 49.
  - Repeated intervals produce higher NP than average power.
  - Ramp uses interpolated watts, not simple endpoint guessing.
  - Missing FTP returns warning/no estimate.

- `planning_analysis_test.go`
  - Event with `workoutDoc` and missing load gets derived planned load.
  - Event with server `TrainingLoad` keeps server value.
  - Forecast uses derived load only when source is local fallback.

- `cmd/icu` tests
  - `workouts calculate --ftp N --desc ...` prints expected JSON.
- `events create --calculate-load --ftp N --desc ...` sends calculated fields.
- `events update <id> --calculate-load --ftp N --desc ...` sends calculated fields.

Feature-specific validation:

1. Use `workouts calculate` on known workout descriptions.
2. Create matching Intervals.icu test events manually or in a controlled athlete calendar.
3. Read events back with `events get` / `events list --resolve`.
4. Compare local duration/TSS/IF against `movingTime`, `icuTrainingLoad`, `icuIntensity`, and `workoutDoc`.
5. Record any systematic differences before enabling auto-fill.

## Non-Goals For First Pass

- No full undocumented Intervals.icu parser clone.
- No HR/pace load formulas.
- No `.zwo`, `.erg`, `.mrc`, or FIT parsing.
- No silent automatic mutation of event load; auto-fill requires `--calculate-load`.
- No external dependencies.

## Decision

The user selected “Parser completo”, “Comparar Intervals”, and “Ambos juntos”. The implementation should include both `workouts calculate` and explicit `events create/update --calculate-load`, with server comparison warnings to keep calibration honest.
