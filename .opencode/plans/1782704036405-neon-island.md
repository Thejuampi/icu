# Plan: Single-Call Coaching Facades

## Goal

Reduce cycling-performance-analysis workflows from many separate `icu` CLI calls to 1-2 aggregate calls that return a stable JSON data contract for the coaching layer.

The facade must prefer measured Intervals.icu data and existing deterministic `icu` analyses. It should bundle data and expose warnings; it should not become a new hidden coaching engine.

## Top Facade Options

1. `icu analysis coaching` — broad coaching/report context for weekly reports and planning reviews. This should be implemented first.
2. `icu analysis workout-context ACTIVITY_ID` — completed workout plus matched plan, surrounding week/block events, NOTE context, and recent readiness/load summary.
3. `icu analysis planning-context` — 12-week history plus next 4-week calendar, optimized for plan generation/review and rebalance decisions.
4. `icu analysis weekly-context` — compact 7-day status report with 42-day wellness and short forward calendar context.
5. `icu analysis athlete-context` — low-frequency athlete/sport/auth/data-source context to avoid repeated `athlete show`, `sports get`, and diagnostics calls.

## Recommended First Implementation

Add `icu analysis coaching` as the primary facade.

Default command:

```bash
icu analysis coaching
```

Explicit planning/report command:

```bash
icu analysis coaching \
  --history-oldest START --history-newest END \
  --plan-oldest NEXT_START --plan-newest NEXT_END \
  --sport-type Ride --resolve
```

Optional adaptation:

```bash
icu analysis coaching --include-adaptation --adaptation-curves 42d,365d
```

## Defaults

- `--history-days 84`
- `--plan-days 28`
- `--sport-type Ride`
- wellness range matches history range
- plan events include NOTE and WORKOUT events by default
- adaptation is opt-in for v1 via `--include-adaptation`
- output is JSON only

## Implementation Steps

1. Add pure context DTOs and builder in `coaching_context.go`.
   - `CoachingContext`
   - `CoachingContextScope`
   - `CoachingContextAnalyses`
   - `CoachingCalendarContext`
   - `CoachingCalendarNote`
   - `CoachingContextDataQuality`
   - `BuildCoachingContext(inputs, options)`

2. Add pure tests in `coaching_context_test.go` first.
   - Builds explicit scope correctly.
   - Extracts NOTE events into `calendar.notes` while preserving all `calendar.events`.
   - Reports source availability and missing sections.
   - Does not invent coaching thresholds or mutate inputs.

3. Add CLI command in `cmd/icu/cmd_analysis.go`.
   - Register `analysis coaching` in `registerAnalysisCommands`.
   - Parse history and plan ranges using existing `trainingPlanDateRanges` behavior where possible.
   - Fetch athlete, sport settings, activities, wellness, and events once.
   - Compute `CyclingAnalysis`, `WellnessAnalysis`, and `TrainingPlanAnalysis` from the fetched inputs.
   - Pass wellness and, when enabled, adaptation into `AnalyzeTrainingPlanWithContext`.
   - Keep HTTP/IO in the CLI layer only.

4. Add CLI tests in `cmd/icu/cmd_analysis_test.go` and/or `cmd/icu/command_functional_test.go`.
   - Command registration.
   - `httptest` fixture proves one command fetches expected endpoints.
   - Explicit date ranges are honored.
   - Default plan range is ISO-week aligned.
   - `--include-adaptation` toggles adaptation output.
   - JSON includes `scope`, `athlete`, `sportSettings`, `analyses`, `calendar.notes`, and `dataQuality`.

5. Update docs.
   - `docs/analysis.md`: new command contract, defaults, data sources, output sections, limitations.
   - `docs/cli-reference.md`: flags and examples.
   - `README.md`: brief mention under analysis commands.
   - `.agents/skills/cycling-performance-analysis/SKILL.md`: prefer `analysis coaching` for weekly/planning workflows, with `analysis workout` as the second call only for specific completed workout reviews.

## Risks

- Output may become large. Mitigation: ship full JSON first; add `--compact` only if needed later.
- Adaptation adds extra endpoints and complexity. Mitigation: make it opt-in in v1.
- Duplicate fetch logic could grow. Mitigation: extract small read helpers only when the command needs them; avoid large abstractions.
- Timezone behavior can be confusing. Mitigation: expose `timezone` and `timezoneSource` in scope and keep explicit date flags documented.
- The facade could become too smart. Mitigation: compose existing deterministic analyses; do not add new coaching decisions in v1.
